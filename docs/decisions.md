# Decisions

이 문서는 프로젝트 결정의 단일 기준점이다. Phase 문서와 README는 결정 내용을 다시 저술하지 않고 `D-xx` ID만 참조한다.

| ID | 결정 | 근거 | 탈락한 대안과 그 이유 |
|---|---|---|---|
| D-01 | Obsidian 볼트의 Markdown을 단일 진실 원천으로 둔다. 웹은 빌드된 JSON과 복사된 자산만 읽는다. | 사용자가 명시한 절대 원칙이다. 웹에서 Markdown을 직접 해석하면 런타임 규칙과 빌드 규칙이 갈라진다. | 웹이 Markdown을 직접 읽기: 정적 호스팅에서 경로와 파서가 불안정하고, 빌드 검증을 우회한다. 별도 CMS: 두 벌의 진실을 만든다. |
| D-02 | 배포는 사내 GitHub Enterprise private repo의 GitHub Pages를 1차 대상으로 한다. 정적 파일만 배포하고 `.nojekyll`을 둔다. | 사내 보안 시스템을 유지하면서 사람이 실행하는 정적 배포에 맞다. GitHub Pages는 서버 런타임이 없으므로 브라우저에 비밀 값을 둘 필요가 없다. | Vercel/Netlify: 사외 서비스 의존이 먼저 생긴다. 사내 nginx/S3: 가능하지만 초기 운영 절차가 더 무겁다. 로컬 전용: 사내 웹사이트 요구를 충족하지 못한다. |
| D-03 | 빌드 타깃은 `internal`과 `public` 두 개다. 캡처마다 `visibility: internal | public`을 갖고 기본값은 `internal`이다. public 번들에는 internal 항목의 메타와 자산을 복사하지 않는다. | 정적 호스팅에는 서버 권한 검사가 없다. 공개용 번들에서 내부 데이터를 물리적으로 제외해야 보안 경계가 된다. | 하나의 번들을 로그인으로 가리기: 정적 사이트 제약을 깨거나 클라이언트에 내부 데이터가 남는다. 지금은 내부 전용만 설계: 사외 확장 요구를 뒤로 미룬다. |
| D-04 | 스택은 Vite + 바닐라 TypeScript + 자체 해시 라우터로 잡는다. | 페이지 수가 적고, JSON 읽기 전용 UI다. 프레임워크 없이도 공유 모듈과 타입 검증을 유지할 수 있다. | React: 확장성은 있지만 초기 코드량과 상태 계층이 늘어난다. Astro: 정적 상세 페이지에는 좋지만 검색 UI와 이중 번들 보안에는 이점이 작다. no-build HTML: TypeScript와 번들 검증을 포기한다. |
| D-05 | 볼트 구조는 `obsidian/captures/<slug>/index.md`와 같은 폴더의 원본 자산으로 한다. | 캡처 노트와 파일이 함께 이동·삭제된다. 상대 경로 검증이 단순하고, Obsidian에서 한 항목을 폴더 단위로 관리하기 쉽다. | 노트와 자산 분리: 대량 관리에는 익숙하지만 링크 깨짐을 더 많이 검증해야 한다. 서비스별 폴더: 서비스명 변경이 곧 파일 이동이다. 플랫 구조: 수백 건에서 산만해진다. |
| D-06 | 수집 포맷은 정지 캡처 `PNG/JPG/WebP`와 모션 캡처 `GIF/MP4/WebM`이다. | 사용자가 모션 포함을 선택했고, 원칙에서 프레임 수 파생을 명시했다. | 정지 이미지만: 모션 사례를 보관하지 못한다. SVG/PDF/Figma URL까지 포함: 초기 스키마와 파생 로직이 커진다. |
| D-07 | 정지 이미지는 원본 그대로 서빙한다. 모션은 갤러리용 대표 프레임만 파생한다. | 사용자가 원본 서빙을 선택했다. 다만 모션을 그리드에 안정적으로 보여주려면 포스터가 필요하고, 포스터는 원본에서 파생 가능하다. | 모든 이미지 썸네일 생성: 선택된 규모 정책보다 무겁다. 원본만 사용하고 포스터 없음: 모션 갤러리의 미리보기가 깨진다. 원본을 웹 번들에서 제외: 상세 원본 뷰 요구와 맞지 않는다. |
| D-08 | 캡처 1건의 분석 항목은 서비스/플랫폼, 화면 유형, UI 패턴, 레이아웃 구조, 톤과 컬러, 타이포, 카피 톤, 인터랙션, 한 줄 인사이트, 태그로 한다. | 사용자가 표준 스키마를 선택했다. 검색 패싯으로 의미가 있으면서 사람이 건별로 작성 가능한 범위다. | 최소 스키마: 검색과 활용 가치가 낮다. 심층 스키마: 접근성 평가와 재현 프롬프트까지 요구해 초기 축적 속도가 떨어진다. |
| D-09 | 페이지는 갤러리, 상세, 컬렉션, 통계, 프롬프트 내보내기로 한다. 인쇄/PDF 내보내기는 이번 범위에서 제외한다. | 사용자가 선택한 페이지 구성이다. 원칙 10은 프롬프트 내보내기에서 미리보기와 클립보드 산출물을 같은 함수로 만들며 지킨다. | 인쇄/PDF 포함: 미리보기와 산출물 동일성 검증 범위가 크게 늘어난다. 홈 대시보드 별도 추가: 갤러리와 통계로 충분하다. |
| D-10 | 자동화 허용 범위는 결정적 파생, 모션 포스터 생성, 스키마 검증, 태그 정규화, 중복 감지 경고다. | 사용자가 선택했다. 모두 사람이 명령을 실행할 때 수행되며, 판단을 대체하지 않는다. | 이미지 의미 분석 자동화: LLM 판단을 자동화해 원칙 2와 3을 위반한다. 자동 배포: 사람이 실행한다는 원칙을 위반한다. |
| D-11 | 이미지 분석, 인덱스 빌드 실행, 배포는 자동화하지 않는다. 사람이 작업창에서 명령을 실행한다. | 사용자가 명시한 절대 원칙이다. 브라우저에 LLM API 키를 두지 않고, 분석은 사람과 작업창에서 수행한다. | 파일 변경 감지 watcher, GitHub Actions 자동 빌드, 자동 배포: 편하지만 사람이 실행한다는 경계를 흐린다. |
| D-12 | 사이트 톤은 도구/정보 맥락이므로 Cool 가족 Blue 세트로 고정한다. `data-theme="cool"`과 `data-mode` light/dark를 사용하고, 세트 전환 UI는 만들지 않는다. | 디자인 시스템에서 도구·정보·데이터 맥락은 Cool로 정의된다. 한 페이지 안에서 톤 세트를 섞지 않는 원칙에도 맞다. | Warm/Violet 테마 전환: 대화·감성 맥락이 아니고 페이지별 톤 혼합 위험이 있다. Mint 전환: 기능은 늘지만 필요가 확정되지 않았다. |
| D-13 | 검색은 200건 이하 기준의 단순 선형 필터와 텍스트 검색으로 시작한다. 검색 라이브러리는 도입하지 않는다. | 사용자가 소규모를 선택했다. 선형 필터가 더 결정적이고 설명하기 쉽다. | Fuse.js 등 검색 라이브러리: 유용하지만 랭킹 규칙을 별도로 이해해야 하고 초기 규모에는 과하다. 서버 검색: 정적 호스팅 제약을 깬다. |
| D-14 | 캡처에서 관찰된 색상 hex는 데이터로 취급한다. 컴포넌트 스타일의 hex는 토큰 파일 한 곳에만 둔다. | 원칙 9는 UI 구현의 색상 원천을 제한한다. 캡처 분석 데이터에는 외부 제품에서 관찰된 hex를 보존해야 한다. | 관찰 색상을 토큰으로 치환: 원본 관찰값을 잃는다. 컴포넌트에 hex 직접 사용: 토큰 원칙을 위반한다. |
| D-15 | GitHub Pages 제약은 계획과 리포트에 반영한다. 게시 사이트 1GB, 리포 권장 1GB, Git 단일 파일 100MB, 배포 타임아웃 10분, 대역폭 월 100GB 소프트 한도를 기준으로 삼는다. | 원본 이미지와 모션을 서빙하므로 용량 한도가 실제 설계 제약이다. 상한·실패·제외는 개수와 이유를 알려야 한다. | 용량을 문서에만 적기: 내용이 늘면 틀어진다. 한도 무시: 사외 확장 시 배포가 깨진다. |
| D-16 | Andrej Karpathy의 LLM Wiki 패턴을 적용한다. `captures`는 raw sources, `obsidian/wiki/`는 LLM이 유지하는 지식층, 이 문서들과 루트 지침은 schema 역할을 한다. | 사용자가 LLM Wiki 개념 적용을 요청했다. 캡처별 분석을 매번 다시 찾는 RAG식 흐름보다, 패턴·서비스·비교 지식을 Markdown에 누적하는 방식이 목적에 맞다. | 검색 전용 JSON: 탐색은 가능하지만 지식이 누적되지 않는다. 임베딩 RAG: 초기 규모와 정적 제약에 비해 인프라가 무겁고 브라우저 키 금지 원칙과 충돌한다. |
| D-17 | LLM Wiki 작업은 `ingest`, `query`, `lint` 세 가지 수동 operation으로 문서화한다. 각 operation은 `obsidian/wiki/index.md`와 `obsidian/wiki/log.md`를 갱신한다. | Karpathy 패턴의 핵심은 index와 log를 통해 LLM이 wiki를 유지하는 것이다. 다만 자동화 금지 원칙 때문에 작업창에서 사람이 요청할 때만 실행한다. | 파일 감지 자동 ingest: 자동화 금지에 걸린다. 채팅 답변만 제공: 좋은 답이 지식층에 누적되지 않는다. log 생략: 나중에 무엇이 갱신됐는지 추적하기 어렵다. |

## 사용자 확인 필요

| 항목 | 확인이 필요한 이유 | 임시 처리 |
|---|---|---|
| Samsung Sharp Sans 라이선스 | public 번들에 폰트를 재배포할 수 있는지 불명확하다. | 계획 문서에는 폰트 라이선스 확인 전 public 번들의 폰트 재배포를 금지한다고 적는다. |
| `ffmpeg`/`ffprobe` 의존 방식 | 모션 프레임 수, 재생 시간, 대표 프레임 파생에 필요하다. 시스템 설치를 전제할지 npm 바이너리를 쓸지 결정해야 한다. | Phase 2에서 사용자 확인 필요로 남긴다. |
| 파생 산출물 커밋 정책 | `dist/`를 같은 브랜치에 커밋할지 Pages 브랜치에만 둘지 배포 절차가 달라진다. | Phase 5에서 두 절차를 비교하고, 구현 전 확정 항목으로 둔다. |
| 사외 공개용 리포·도메인 | public 번들의 실제 배포 위치가 정해져야 링크와 base path를 확정할 수 있다. | 해시 라우터와 상대 경로를 기본으로 둔다. |
| 실제 캡처 규모 | 원본 서빙 정책이 1GB 한도에 얼마나 빨리 닿는지 아직 측정 불가하다. | Phase 2 리포트에서 총 바이트와 잔여 용량을 매번 출력한다. |
